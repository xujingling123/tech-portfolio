> 
> A. 行为模型
> 
> **B. 领域模型**
> 
> C. 专家模型
> 
> D. 知识库模型
> 
> 解析：
> 
> 领域驱动设计（Domain-Driven Design，DDD）的核心思想是 围绕领域模型（Domain Model）开展软件设计与开发。领域模型是对业务领域知识的抽象，由开发人员与领域专家协作构建，用于精准捕捉领域内的概念、关系与规则。
> 
> *   选项 A “行为模型” 侧重描述系统行为，并非 DDD 的核心围绕对象；
> *   选项 C “专家模型” 强调 “专家” 本身的模型，不符合 DDD 对 “领域知识抽象” 的核心聚焦；
> *   选项 D “知识库模型” 聚焦知识的存储与管理，并非 DDD 的核心模型。
> 
> 综上，答案为 **B**。

> 以下关于微服务架构与面向服务架构的描述中，正确的是（）。
> 
> A. 两者均采用去中心化管理
> 
> B. 两者均采用集中式管理
> 
> **C. 微服务架构采用去中心化管理，面向服务架构采用集中式管理**
> 
> D. 微服务架构采用集中式管理，面向服务架构采用去中心化管理
> 
> 解析：
> 
> *   **微服务架构**：强调**去中心化管理**。每个微服务独立开发、部署、运维，服务间通过轻量级通信（如 HTTP、消息队列）交互，无集中式的 “服务总线” 或强管控中心，各服务可自主演进。
> *   **面向服务架构（SOA）**：通常采用**集中式管理**。依赖 “企业服务总线（ESB）” 等集中式组件，统一管理服务的通信、路由、协议转换等，服务的注册、治理更倾向于集中控制。
> 
> 因此，微服务架构采用去中心化管理，面向服务架构采用集中式管理，答案为 **C**。

> 在 UML2.0（Unified Modeling Language）中，顺序图用来描述对象之间的消息交互，其中循环、选择等复杂交互使用（）表示。
> 
> A. 嵌套
> 
> B. 泳道
> 
> C. 组合
> 
> **D. 序列片段**
> 
> 解析：
> 
> 在 UML2.0 的顺序图中：
> 
> *   **序列片段（Sequence Fragment）** 是用于表示复杂交互（如循环、选择、并行等）的核心机制。通过为序列片段指定操作符（如 `loop` 表示循环，`alt` 表示选择 / 分支），可清晰描述对象间的复杂消息交互逻辑。
> *   “嵌套” 并非 UML2.0 顺序图中定义复杂交互的标准方式；“泳道” 主要用于划分交互的职责范围（如不同参与者的交互区域），不直接表示循环、选择；“组合” 更多应用于结构建模（如类的组合关系），与顺序图的复杂交互表示无关。
> 
> 综上，答案为 **D**。

> 在 UML2.0（Unified Modeling Language）中，顺序图用来描述对象之间的消息交互，对象之间的消息类型包括（）。
> 
> A. 同步消息、异步消息、返回消息、动态消息、静态消息
> 
> B. 同步消息、异步消息、动态消息、参与者创建消息、参与者销毁消息
> 
> C. 同步消息、异步消息、静态消息、参与者创建消息、参与者销毁消息
> 
> **D. 同步消息、异步消息、返回消息、参与者创建消息、参与者销毁消息**
> 
> 解析：
> 
> UML2.0 顺序图中，对象之间的**标准消息类型**包括：
> 
> *   **同步消息**：发送者发送消息后需等待接收者响应，直到收到返回结果才继续执行；
> *   **异步消息**：发送者发送消息后无需等待，可继续自身流程；
> *   **返回消息**：对同步消息的响应，用于将结果回传给发送者；
> *   **参与者创建消息**：用于创建参与者对象；
> *   **参与者销毁消息**：用于销毁参与者对象。
> 
> “动态消息”“静态消息” 并非 UML2.0 顺序图定义的标准消息类型，因此排除含这些表述的选项（A、B、C）。
> 
> 综上，答案为 **D**。

> 以下有关构件特性的描述中，说法**不正确**的是（）。
> 
> A. 构件是独立部署单元
> 
> B. 构件可作为第三方的组装单元
> 
> C. 构件没有外部的可见状态
> 
> **D. 构件作为部署单元，是可拆分的**
> 
> 解析：
> 
> 构件（Component）的核心特性包括：
> 
> *   **独立部署单元**：构件是可单独部署的软件单元（如 Java 的 JAR 包、.NET 的程序集等），因此选项 A 正确。
> *   **第三方组装单元**：构件为软件复用设计，可被第三方在系统组装时集成使用，因此选项 B 正确。
> *   **封装内部状态**：构件的内部状态对外封装，外部仅通过接口交互，无 “外部可见状态”，因此选项 C 正确。
> *   **不可拆分的部署单元**：构件作为**独立、完整**的部署单元，部署时需以整体形式存在，**不能拆分**后部署。因此选项 D 中 “可拆分” 的描述错误。
> 
> 综上，答案为 **D**。

> 在构件的定义中，（）是一个已命名的一组操作的集合。
> 
> **A. 接口**
> 
> B. 对象
> 
> C. 函数
> 
> D. 模块
> 
> 解析：
> 
> *   **接口**：在构件（或面向对象、服务化等场景）中，接口的核心定义是 “已命名的一组操作（方法、服务等）的集合”，用于规定构件对外提供的功能契约，符合题意。
> *   **对象**：对象包含**状态（数据）和行为（操作）**，并非仅 “一组操作的集合”，还涉及数据封装，因此不符合。
> *   **函数**：函数是**单个操作**（完成特定功能的代码段），不是 “一组操作的集合”，因此不符合。
> *   **模块**：模块是对软件的**逻辑划分**（用于组织代码、解耦功能），并非专门指代 “一组操作的集合”，因此不符合。
> 
> 综上，答案为 **A**。

> 在服务端构件模型的典型解决方案中，（）较为适用于应用服务器。
> 
> **A. EJB 和 COM + 模型**
> 
> B. EJB 和 servlet 模型
> 
> C. COM + 和 ASP 模型
> 
> D. COM + 和 servlet 模型
> 
> 解析：
> 
> 服务端构件模型需支撑企业级应用的分布式、事务性等复杂需求：
> 
> *   **EJB（Enterprise JavaBeans）**：是 Java EE 平台的核心企业级构件模型，专为**应用服务器**设计，用于封装业务逻辑、支持分布式事务、资源管理等企业级能力。
> *   **COM+**：微软的组件模型扩展，为 Windows 环境下的**应用服务器**提供组件服务（如事务管理、安全、对象池等），是企业级构件的典型技术。
> *   **servlet**：属于 Web 层技术，聚焦 HTTP 请求处理，并非服务端 “构件模型” 层面（用于应用服务器核心业务构件封装）的典型代表。
> *   **ASP**：是 Web 应用开发技术（而非构件模型），不具备构件模型的封装、复用等核心特性。
> 
> 因此，**EJB 和 COM + 模型**均是适用于应用服务器的服务端构件模型，答案为 **A**。

> 以下有关构件演化的叙述中，说法**不正确**的是（）。
> 
> A. 安装新版本构件可能会与现有系统发生冲突
> 
> B. 构件通常也会经历一般软件产品具有的演化过程
> 
> C. 解决 “遗留系统移植” 问题还需要通过使用包裹器构件来适配旧版软件
> 
> **D. 为安装新版本的构件，必须终止系统中所有现有版本构件的运行**
> 
> 解析：
> 
> 构件演化支持**灵活的更新机制**（如热部署、多版本共存等），并非必须终止所有现有构件运行：
> 
> *   **热部署**：可在系统运行时替换构件，无需停止整个系统；
> *   **多版本管理**：系统可同时加载新旧版本构件，逐步切换依赖，无需全部终止现有构件。
> 
> 对各选项的分析：
> 
> *   **选项 A**：新版本构件与现有系统的接口、依赖等可能不兼容，因此可能发生冲突，表述正确。
> *   **选项 B**：构件作为软件单元，和普通软件产品一样，会因需求变更、技术迭代等经历演化过程，表述正确。
> *   **选项 C**：“包裹器（Wrapper）构件” 可封装旧系统接口，实现遗留系统与新环境的适配，是遗留系统移植的常用手段，表述正确。
> *   **选项 D**：构件演化支持热部署或多版本并行等方式，**无需 “必须终止所有现有版本构件运行”**，表述错误。
> 
> 综上，答案为 **D**。

> 软件复杂性度量中，（）可以反映源代码结构的复杂度。
> 
> A. 模块数
> 
> **B. 环路数**
> 
> C. 用户数
> 
> D. 对象数
> 
> 解析：
> 
> 软件复杂性度量需针对**源代码结构本身的逻辑复杂度**进行评估：
> 
> *   **选项 A（模块数）**：模块数体现软件的模块化分解程度，而非源代码结构内部的复杂度，因此不符合。
> *   **选项 B（环路数）**：通常指 “环路复杂度（Cyclomatic Complexity）”，它通过计算程序中独立路径的数量，反映代码中判断、循环等控制结构的复杂程度，是衡量源代码结构复杂度的经典指标，因此符合题意。
> *   **选项 C（用户数）**：用户数与软件的使用规模相关，和源代码结构复杂度无关，因此不符合。
> *   **选项 D（对象数）**：对象数是面向对象系统中对象的数量，仅体现对象的数量规模，不直接反映源代码结构的复杂度（如类的层次、方法的逻辑等才是结构复杂度的核心），因此不符合。
> 
> 综上，答案为 **B**。

> 在白盒测试中，测试强度最高的是（）。
> 
> A. 语句覆盖
> 
> B. 分支覆盖
> 
> C. 判定覆盖
> 
> **D. 路径覆盖**
> 
> 解析：
> 
> 白盒测试的覆盖强度（即测试的全面性、发现错误的能力）与覆盖范围的广度正相关，不同覆盖准则的强度从低到高依次为：
> 
> *   **语句覆盖**：仅要求每个可执行语句至少执行一次，覆盖范围最窄，强度最低。
> *   **判定（分支）覆盖**：要求每个判断的 “真”“假” 分支至少执行一次，覆盖强度高于语句覆盖，但仍未覆盖所有可能的执行路径。
> *   **路径覆盖**：要求覆盖程序中**所有可能的执行路径**，是白盒测试中覆盖范围最广、对代码逻辑检验最彻底的方式，因此测试强度最高。
> 
> 综上，答案为 **D**。

> 在黑盒测试方法中，（）方法最适合描述在多个逻辑条件取值组合所构成的复杂情况下，分别要执行哪些不同的动作。
> 
> A. 等价类
> 
> B. 边界值
> 
> **C. 判定表**
> 
> D. 因果图
> 
> 解析：
> 
> 黑盒测试各方法的核心特点如下：
> 
> *   **等价类划分**：将输入数据划分为等价类，从每个类中选代表值测试，侧重 “数据分类简化测试”，不针对**多条件组合与动作的对应关系**，因此不符合。
> *   **边界值分析**：聚焦输入 / 输出的 “边界数值”（如最大值、最小值附近），用于发现边界处的错误，与 “多条件组合的动作逻辑” 无关，因此不符合。
> *   **判定表**：由 “条件桩（所有输入条件）、动作桩（所有可能动作）、条件项（条件的取值组合）、动作项（对应组合的动作）” 组成，**天然适合描述 “多逻辑条件组合 → 不同动作” 的复杂逻辑**，能清晰枚举所有条件组合及其对应的动作，因此符合题意。
> *   **因果图**：用于分析 “原因（输入条件）” 与 “结果（输出动作）” 的因果关系，是生成判定表的 “前期分析工具”，而非直接 “描述多条件组合与动作” 的载体，因此不符合。
> 
> 综上，答案为 **C**。

> （）的目的是测试软件变更之后，变更部分的正确性和对变更需求的符合性，以及软件原有的、正确的功能、性能和其它规定的要求的不损害性。

> 
> B. Alpha 测试
> 
> C. Beta 测试

> 解析：
>

> *   **选项 B（Alpha 测试）**：是由开发团队内部在**开发环境**下进行的早期测试，目的是发现缺陷，不聚焦 “变更后的兼容性与原有功能保护”，因此不符合。
> *   **选项 C（Beta 测试）**：是由用户在**实际使用环境**下进行的测试，用于收集用户反馈，与 “软件变更后的回归验证” 无关，因此不符合。

> 
> 综上，答案为 **D**。

> 在对遗留系统进行评估时，对于技术含量较高、业务价值较低且仅能完成某个部门的业务管理的遗留系统，一般采用的遗留系统演化策略是（）策略。
> 
> A. 淘汰
> 
> B. 继承
> 
> **C. 集成**
> 
> D. 改造
> 
> 解析：
> 
> 遗留系统演化策略的适用场景需结合**技术价值**与**业务价值**判断：
> 
> *   **淘汰策略**：适用于**业务价值低且技术陈旧**的系统，直接废弃。但本题系统 “技术含量较高”，直接淘汰会浪费技术价值，因此不适用。
> *   **继承策略**：适用于**业务价值高且技术仍可支撑**的系统，直接保留复用。但本题系统 “业务价值较低”，无需重点继承，因此不适用。
> *   **集成策略**：适用于 技术有价值，但业务范围窄（如仅部门级）的系统。可通过集成技术，将该系统作为组件整合到更大的系统中，既利用其技术优势，又扩展业务覆盖范围。本题系统 “技术含量高、业务价值低且仅部门可用”，符合集成策略的适用场景。
> *   **改造策略**：适用于**业务价值高，但技术陈旧**的系统，通过改造技术以更好支撑业务。但本题系统 “技术含量高”，无需改造技术，且 “业务价值低”，改造投入产出比低，因此不适用。
> 
> 综上，答案为 **C**。

> 在软件体系结构的建模与描述中，多视图是一种描述软件体系结构的重要途径，其体现了（A）的思想；同时，“4+1 模型” 是描述软件体系结构的常用模型，该模型中 “1” 指的是（）。
> 
> **A. 关注点分离**
> 
> B. 面向对象
> 
> C. 模型驱动
> 
> D. UML
> 
> 解析：
> 
> *   **多视图的思想体现**：软件体系结构的**多视图方法**，核心是将体系结构的不同 “关注点”（如逻辑结构、进程交互、物理部署、开发组织等）分离到不同视图中分别描述，以此降低复杂度、清晰表达各维度特性，这体现了**关注点分离**的思想（选项 A 正确）。
> *   **“4+1 模型” 的 “1”**：在 “4+1 模型” 中，“4” 代表四个主要视图（逻辑视图、进程视图、物理视图、开发视图），而 “1” 指**用例视图**—— 通过用例和场景驱动其他四个视图的设计（用例捕获了系统核心功能需求，是体系结构构建的核心驱动力）。
> 
> 选项 B “面向对象” 是编程 / 设计范式，并非多视图的核心思想；选项 C “模型驱动” 强调以模型为中心的开发，与 “分离关注点” 的多视图逻辑不符；选项 D “UML” 是建模语言（多视图可通过 UML 表达，但不是多视图体现的思想本身）。
>
