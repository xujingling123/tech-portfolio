---> 下列属于开发期质量属性的是 ( D)。
> 
> A. 安全性
> 
> B. 可伸缩性
> 
> C. 互操作性
> 
> **D. 可移植性**
> 
> 解析：
> 
> 软件质量属性可分为**开发期质量属性**和**运行期质量属性**：
> 
> *   **开发期质量属性**：关注软件开发、维护阶段的便利性，如可移植性（使软件能便捷地从一个开发环境 / 平台迁移到另一个）、可维护性等。
> *   **运行期质量属性**：关注系统运行时的特性，如安全性（保护系统免受未授权访问等）、可伸缩性（系统应对负载变化的能力）、互操作性（与其他系统交互的能力）等。
> 
> 因此，安全性、可伸缩性、互操作性属于**运行期质量属性**；可移植性属于**开发期质量属性**。

> 操作系统内核，通常包括的功能有（）。
> 
> **A. 进程管理、文件系统管理、设备驱动管理、内存管理**
> 
> B. 进程管理、文件系统管理、网络管理、安全管理
> 
> C. 文件管理、设备管理、内存管理、用户管理
> 
> D. 进程管理、内存管理、网络管理、文件管理  
> 解析:
> 
> 操作系统内核负责最核心的系统资源管理与硬件交互，其典型核心功能包括：
> 
> *   **进程管理**：负责进程的创建、调度、同步与通信等，是 CPU 资源管理的核心。
> *   **内存管理**：管理内存的分配、回收，以及地址映射（如虚拟内存与物理内存的转换）等，保障内存资源的高效利用。
> *   **设备驱动管理**：直接与硬件设备交互，为上层提供统一的设备访问接口，是硬件与软件之间的 “桥梁”。
> *   **文件系统管理**：管理文件的存储、组织、访问权限等，实现对外部存储资源的有效管理。
> 
> 而**网络管理**（属于上层网络服务范畴）、**安全管理**（多为系统上层的权限 / 安全策略管理）、**用户管理**（账户、权限等上层管理），通常不属于内核最核心的功能模块，而是操作系统上层服务或子系统的功能。
> 
> 综上，选项 A 涵盖了操作系统内核最典型的核心功能。

> 信息系统架构风格是描述某一特定应用领域中系统组织方式的惯用模式。架构风格定义了一个系统家族，即一个架构定义（C）。
> 
> A. 一组设计原则
> 
> B. 一组模式
> 
> **C. 一个词汇表和一组约束**
> 
> D. 一组最佳实践
> 
> 解析：
> 
> 架构风格的核心定义是：为一组具有相同结构属性的架构，定义**一个词汇表**（用于描述架构的组成元素及元素间的关系）和**一组约束**（规定这些元素与关系如何组织、组合），从而确定一个 “系统家族” 的结构特征。
> 
> *   选项 A：“设计原则” 是抽象的指导思想，并非架构风格定义系统家族的直接方式。
> *   选项 B：“一组模式” 是架构风格的组成部分，但不足以完整定义 “系统家族”（缺少词汇表和约束的明确规则）。
> *   选项 C：符合架构风格的定义，通过 “词汇表（描述元素 / 关系）+ 约束（组织规则）” 定义系统家族。
> *   选项 D：“最佳实践” 是经验总结，不是架构风格定义系统家族的核心要素。

> 在业务流程分析中，( ) 是一种从流程的角度出发描述和分析复杂系统的模型工具。
> 
> A. DEMO
> 
> **B. Petri 网**
> 
> C. BPM
> 
> D. IDEF
> 
> 解析：
> 
> *   **选项 A：DEMO**DEMO（动态企业建模）侧重于企业整体建模的框架体系，并非专门从 “流程角度” 描述复杂系统的模型工具。
>     
> *   **选项 B：Petri 网**Petri 网是一种离散并行系统的数学建模工具，能精准描述流程中的事件、状态流转、并发交互等动态行为，非常适合从流程视角分析复杂系统的运行逻辑（如流程中的同步、竞争、时序等关系），是业务流程分析的典型模型工具。
>     
> *   **选项 C：BPM**BPM 是 “业务流程管理（Business Process Management）” 的缩写，代表的是一种管理方法 / 体系，而非具体的 “模型工具”。
>     
> *   **选项 D：IDEF**IDEF（集成定义方法）主要用于系统分析与设计（如 IDEF0 用于功能建模、IDEF1X 用于数据建模），虽可涉及流程相关内容，但并非专门从 “流程角度” 描述复杂系统的典型模型工具，对流程动态性的描述能力弱于 Petri 网。
>     

> 软件工程过程是指为获得软件产品，由软件工程师完成的一系列软件工程活动，包括以下 4 个方面（）。
> 
> A. 计划、设计、编码、测试
> 
> **B. 计划、执行、检查和处理**
> 
> C. 计划、开发、构建、测试
> 
> D. 计划、设计、执行、检查
> 
> 解析：
> 
> 软件工程过程借鉴了 PDCA 循环（戴明环）的管理思想，PDCA 循环包含四个核心环节：
> 
> *   **计划（Plan）**：明确目标、制定活动计划与流程。
> *   **执行（Do）**：按照计划实施软件工程活动（如开发、测试等具体工作）。
> *   **检查（Check）**：评估执行结果，对比目标与实际情况，发现偏差或问题。
> *   **处理（Act）**：对检查中发现的问题进行分析、改进，将有效措施标准化，为下一个循环提供优化依据。
> 
> 选项 A 是**软件开发阶段**（而非软件工程过程的管理环节）；选项 C 的 “开发、构建” 划分模糊且不符合 PDCA 逻辑；选项 D 缺少 “处理” 环节，不满足 PDCA 循环的完整性。只有选项 B 符合 PDCA 循环对软件工程过程的覆盖。

> 操作系统中 ( ) 是资源分配和管理的最小单位。
> 
> **A. 进程**
> 
> B. 线程
> 
> C. 作业
> 
> D. 程序段
> 
> 解析：
> 
> 在操作系统中：
> 
> *   **进程**：是资源分配和管理的**最小单位**。操作系统会为每个进程独立分配资源（如内存空间、文件描述符、系统资源等），进程也是调度的基本单位之一。
> *   **线程**：是**调度的基本单位**，但线程本身不具备独立的资源分配能力，它共享所属进程的资源。
> *   **作业**：是用户向系统提交的 “任务集合”，包含程序、数据及执行需求，并非资源分配的最小粒度。
> *   **程序段**：是程序的一部分代码片段，仅体现指令逻辑，不涉及操作系统的资源分配与管理。

> ( ) 设计规定软件设计人员应为软件组件定义正式、精确和可验证的接口规范。
> 
> **A. 契约式**
> 
> B. 面向对象
> 
> C. 结构化
> 
> D. 原型
> 
> 解析：
> 
> *   **契约式设计（Design by Contract，DbC）**：核心思想是为软件组件（如类、模块）定义**正式、精确且可验证的 “契约”**（包括接口的前置条件、后置条件和不变式等），以此规范组件间的交互，确保组件行为的可靠性与可验证性，符合题干中 “定义正式、精确和可验证的接口规范” 的描述。
> *   **面向对象设计**：围绕 “对象”“类”“继承” 等概念组织设计，虽涉及接口定义，但并非以 “契约式” 的 “精确可验证接口规范” 为核心特征。
> *   **结构化设计**：通过模块分解、功能划分来组织系统，注重模块间的调用关系，不强调 “正式、精确且可验证” 的接口契约定义。
> *   **原型设计**：属于迭代式的设计方法（先构建原型再迭代完善），与 “为组件定义正式接口规范” 的目标无关。

> M2M 涉及若干重要的技术部分，分别是 ( )。
> 
> **A. 智能化机器、M2M 硬件、通信网络、中间件、应用**
> 
> B. 智能化设备、M2M 软件、网络、云平台
> 
> C. 传感器、执行器、网络设备、中央处理系统
> 
> D. 终端设备、网络、中心管理系统、数据库
> 
> 解析：
> 
> M2M（Machine-to-Machine，机器对机器）技术体系的核心组成包括：
> 
> *   **智能化机器 / 设备**：具备感知、计算或控制能力的终端实体，是 M2M 的 “源头”。
> *   **M2M 硬件**：如嵌入式模块、通信模块等，为设备提供联网与数据交互的硬件基础。
> *   **通信网络**：包括各类有线 / 无线网络（如蜂窝网络、物联网专用网络等），承担设备间或设备与平台间的数据传输任务。
> *   **中间件**：负责数据处理、设备管理、协议转换等，是连接底层设备与上层应用的 “桥梁”。
> *   **应用**：基于 M2M 数据实现业务逻辑（如远程监控、智能控制等），为用户提供价值。
> 
> 选项 B 中的 “云平台”、选项 C 的 “中央处理系统”、选项 D 的 “数据库” 并非 M2M 技术体系**最核心、最基础**的分类组成；而选项 A 完整覆盖了 M2M 从终端、硬件、网络、中间层到应用层的关键技术部分。

> 在 M2M 技术中，对获得的数据进行加工分析，提供决策依据的是（）。
> 
> A. 智能化机器
> 
> B. 网络设备
> 
> C. 中间件
> 
> **D. 应用**
> 
> 解析：
> 
> M2M（Machine-to-Machine，机器对机器）技术体系中，各部分功能分工不同：
> 
> *   **智能化机器**：主要负责**数据采集**或执行具体操作（是数据的 “源头” 或动作执行者），不承担数据的 “加工分析、决策支持”。
> *   **网络设备**：核心作用是**传输数据**（在设备、中间件、应用间传递信息），不涉及数据的分析加工。
> *   **中间件**：聚焦于**数据的中间处理**（如协议转换、设备管理、数据初步整合等），但并非最终 “加工分析数据以提供决策依据” 的环节。
> *   **应用**：针对具体业务场景，对收集到的数据进行**深度加工、分析**，并基于分析结果生成决策依据（如远程监控中的异常预警、智能运维中的策略推荐等），直接支持业务决策或智能控制。

> 根据 DO-178 标准，软件生命周期过程包括（）。
> 
> A. 目标、活动、证据
> 
> **B. 指导、目标、活动、证据**
> 
> C. 规划、开发、确认、监控
> 
> D. 需求、设计、代码、测试
> 
> 解析：
> 
> DO-178 标准（航空航天领域软件认证标准，如 DO-178B）中，**软件生命周期过程**的核心构成包括：
> 
> *   **指导（Guidance）**：涵盖计划、管理等对过程的引导性工作；
> *   **目标（Objectives）**：明确每个过程需要达成的目的；
> *   **活动（Activities）**：过程中具体执行的任务与操作；
> *   **证据（Evidence）**：过程中需产生的文档、验证材料等，用于证明过程符合要求。
> 
> 其他选项分析：
> 
> *   选项 A：缺少 “指导”，不完整；
> *   选项 C：“规划、开发、确认、监控” 是通用项目管理 / 开发阶段分类，非 DO-178 标准定义的生命周期过程构成；
> *   选项 D：“需求、设计、代码、测试” 是软件开发的**阶段活动**，并非整个生命周期过程的构成要素。

> CDN 和反向代理的基本原理都是 ( )。
> 
> **A. 缓存**
> 
> B. 负载均衡
> 
> C. 路由转发
> 
> D. NAT 转换
> 
> 解析：
> 
> *   **CDN（内容分发网络）**：核心原理是将静态内容（如网页、视频等）**缓存**到分布在全球 / 各地的边缘节点服务器，用户请求时可从最近的缓存节点获取内容，减少延迟、提升访问效率。
> *   **反向代理**：位于服务器端，会**缓存**静态资源（如页面、文件），客户端请求到达时，若缓存中有目标资源，直接返回缓存内容，无需穿透到后端服务器，从而减轻后端压力、加速响应。
> 
> 两者的**基本原理核心是 “缓存”**（负载均衡是它们可附带的功能，但非最基本原理；路由转发、NAT 转换与二者核心机制无关）。

> 下列 ( ) **不属于**专利许可的类型。
> 
> A. 独占许可
> 
> B. 排他实施许可
> 
> C. 普通实施许可
> 
> **D. 特殊许可**
> 
> 解析：
> 
> 专利许可的**典型类型**包括：
> 
> *   **独占许可**：被许可方在约定时间、地域内独占实施专利，许可方自身也不得实施。
> *   **排他实施许可**（独家许可）：许可方与被许可方均可实施专利，但许可方不得再许可第三方实施。
> *   **普通实施许可**：许可方可在同一范围许可多个被许可方实施专利，被许可方权利相对宽松。
> 
> 而 “特殊许可” 并非专利许可的**法定或公认的典型类型**，无明确、统一的定义与范畴。

> 关于局域网的说法，**错误**的是 ( )。
> 
> A. 性能更稳定框架简易
> 
> B. 覆盖范围小
> 
> C. 拓扑结构种类多样
> 
> **D. 非封闭性网**
> 
> 解析：
> 
> 局域网（Local Area Network，LAN）的主要特点分析如下：
> 
> *   **选项 A**：局域网覆盖范围小、网络结构相对简单，因此性能通常更稳定，架构框架也较为简易，该说法正确。
> *   **选项 B**：局域网的定义就是 “局部区域内的计算机网络”，覆盖范围通常较小（如办公室、校园、企业内部等），该说法正确。
> *   **选项 C**：局域网的拓扑结构可以是总线型、星型、环型、树型等多种类型，种类较为多样，该说法正确。
> *   **选项 D**：局域网是**封闭性网络**，通常局限于特定区域（如企业、机构内部），由特定用户群体使用和管理，并非 “非封闭性网”，该说法错误。

> 如果服务器的功能较弱而工作站（客户端）的功能较强，则称为 ( ) 架构模式。
> 
> A. 胖客户端 / 胖服务器
> 
> B. 瘦客户端 / 瘦服务器
> 
> **C. 胖客户端 / 瘦服务器**
> 
> D. 瘦客户端 / 胖服务器
> 
> 解析：
> 
> 在客户端 / 服务器（C/S）架构模式中：
> 
> *   **胖客户端**：客户端承担大量业务逻辑、数据处理或界面渲染等工作，功能强大。
> *   **瘦客户端**：客户端仅负责简单显示与交互，核心逻辑由服务器承担，功能薄弱。
> *   **胖服务器**：服务器承担大量业务逻辑、数据处理等，功能强大。
> *   **瘦服务器**：服务器功能较弱，仅提供简单服务，核心逻辑由客户端承担。
> 
> 题目中 “服务器功能较弱，工作站（客户端）功能较强”，对应  胖客户端（功能强）+ 瘦服务器（功能弱）的组合。
